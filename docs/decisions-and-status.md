# 결정사항과 구현 현황

이 문서는 설계 대화에서 합의한 내용과 현재 코드의 구현 범위를 구분하여
기록한다. 대화 원문이 아니라 재검토 가능한 결정사항만 정리한다.

## 합의된 결정

- 모든 대상 서버는 단일 `linux_servers` 인벤토리 그룹으로 관리한다.
- 대상 서버의 Ansible 접속 계정은 `ansible-admin`으로 통일한다.
- 컨트롤 노드에는 같은 이름의 로컬 계정을 요구하지 않으며 전용 개인키만
  안전하게 보관한다.
- bootstrap은 `hosts.yml`·서버별 Vault 일괄 방식과 IP 직접 지정·암호 입력
  개별 방식을 모두 지원한다.
- SSH 공개키 인증과 비대화형 sudo를 사용한다.
- 로깅 정책과 로그인/PAM 정책은 별도 플레이북과 Role로 관리한다.
- 자산 진단 체크 조치는 취약점 코드와 OS별 플레이북으로 분리한다.
- 하나의 설정은 하나의 취약점 플레이북만 변경하며 기존 통합 플레이북에서
  중복 적용하지 않는다. 읽기 전용 사전점검은 유지한다.
- 시간 동기화 클라이언트는 chrony로 통일한다.
- 기존 `systemd-timesyncd`, `ntp`, `ntpd` 서비스는 중지·비활성화·마스킹한다.
- 외부 NTP 소스는 `time.kaist.ac.kr`, `time.nist.gov`을 우선 사용한다.
- 모든 서버에 동일한 로깅 정책을 적용하며 현재 기본 프로필은 `raw`이다.
- 설정 배포와 정기 검증은 Ansible이 담당한다.
- 실시간 이벤트 분석과 경보는 중앙 로그/SIEM이 담당한다.
- 실제 서버 정보 확인 전에는 PAM 및 SSH 인증 차단 정책을 적용하지 않는다.
- 로그인 정책은 서버별 `serial: 1`로 적용하고 PAM 변경을 위해 재부팅하지 않는다.
- SSH 설정 변경은 구문검사 후 OS별 서비스 반영 방식을 사용하며 기존 관리자
  세션을 유지한다.
- audit immutable 모드(`-e 2`)는 초기 기본값을 비활성화하여 정책 변경에
  재부팅이 필요하지 않도록 한다.

## 현재 구현 완료

- 단일 그룹 인벤토리 예시
- 기존 관리자 계정으로 `ansible-admin` 시스템 계정·전용 공개키·검증된
  sudoers를 구성하고 새 계정으로 재접속 검증하는 bootstrap
- bootstrap 최초 접속 계정과 새 관리계정 검증 계정을 분리한 두 가지 실행 경로
- 10대 배치마다 관리계정 구성 직후 공개키 재접속·sudo를 검증하고 실패 시
  다음 배치를 중단하는 bootstrap 처리 순서
- SSH, Python, sudo 연결 사전점검
- 최초 등록용 OS·보안 관련 서비스·파일시스템·보안 구성요소 현황수집
- 정책 적용 전 SSH·PAM·계정·audit·로그 용량 사전점검
- `/etc/issue`, `/etc/issue.net` 경고문
- SSH Banner와 `LogLevel VERBOSE`
- 일반·시리얼 콘솔의 호스트명 비노출
- Ubuntu/Debian SSH 배포판 버전 정보 비노출
- chrony 패키지, 설정 및 서비스 관리
- Ubuntu/Debian apt 캐시 갱신과 기존 시간 동기화 서비스 비활성화
- auditd 설치와 기본 감사 규칙
- journald 영구 저장과 용량·기간 설정
- 선택적 rsyslog 중앙 전달 템플릿
- 주간 로그 용량 및 audit 상태 점검
- 월간 chrony 시간 오차 점검
- 반기 네트워크 소켓 현황수집
- 분기 또는 반기 계정·관리자·로그인·잠금·만료 현황수집
- 사전점검과 정기점검 보고서의 날짜·실행시각별 보존
- U0309 root SSH 직접 접속 제한의 Red Hat 계열·Ubuntu별 플레이북
- U0309의 Telnet TCP/23 및 관련 파일 읽기 전용 현황 확인

## 부분 구현

- 로그 관리자 통제: 그룹과 일부 파일 권한만 있으며 관리자 명단과 sudo 정책이 없다.
- 1년 보존: journald 기간은 설정하지만 4GB 제한 및 audit/logrotate 정책 때문에
  전체 로그의 1년 보존을 보장하지 않는다.
- 로그 무결성: audit 규칙 파일 체크섬을 계산하지만 승인 기준값과 비교하지 않는다.
- 접근 감사: OS 파일 접근 실패와 중요 설정 변경은 기록하지만 업무 데이터,
  데이터베이스, 애플리케이션 권한 실패는 제품별 설정이 필요하다.
- 네트워크 점검: 현재 목록을 수집하지만 승인 목록 또는 이전 결과와 비교하지 않는다.
- 중앙 로그: 주소와 인증서가 확정되지 않아 기본적으로 비활성화되어 있다.
  현재 TLS 템플릿은 `anon` 인증 모드이므로 CA 기반 서버 인증을 제공하지 않는다.

## 미구현

- 로그인/PAM 정책 Role
- cron 작업의 실제 실행 감사
- 패키지 설치·삭제·업데이트 감사 규칙
- SUID/SGID 및 관리자 서비스 사용 시도 감사
- AIDE 기준 DB와 무결성 비교
- 중앙 로그 저장소의 유형별 보존정책
- 실시간 이상행위 탐지와 알림
- AWX/AAP 또는 CI의 정기 실행 스케줄

## 설계 완료, 실행 코드 미반영

- audit 규칙을 로그인, 설정 변경, 접근 실패, 권한 명령, 패키지·cron,
  사용자 명령 및 최종 잠금 파일로 분리하는 구조
- auditd, journald, rsyslog의 1년 보존 용량 산정과 장애 대응 기준
- OS별 로그인/PAM Role 구조와 무재부팅·단일 서버 순차 적용 절차

## 적용 전 필수 확인

- 실제 대상 IP와 SSH 호스트 키
- bootstrap에 사용할 기존 관리자 계정의 SSH·sudo와 별도 복구경로
- 대상 OS 및 Python 버전
- 패키지 저장소 접근 가능 여부
- NTP 호스트 DNS와 UDP/123 응답
- 기존 chrony 설정과 업무상 필수 옵션
- 중앙 로그 서버, TLS 인증서와 신뢰할 CA
- 서버별 `/var/log` 용량과 일평균 로그 발생량
