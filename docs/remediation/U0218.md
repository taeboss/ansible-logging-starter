# U0218 - /etc/hosts.allow, /etc/hosts.deny 설정

## 진단 기준

- 양호: `/etc/hosts.allow`와 `/etc/hosts.deny`의 소유자가 `root`이고 다른
  사용자에게 쓰기 권한이 없으며, `/etc/hosts.deny`에 `ALL: ALL`이 설정되고
  `/etc/hosts.allow`에 승인된 서비스와 접근 원천이 등록되어 있다.
- 취약: 두 파일의 소유자·권한이 기준과 다르거나, 기본 차단 및 승인된 접근
  허용 규칙이 설정되지 않았다.

TCP Wrapper를 지원하는 서비스에서는 `/etc/hosts.allow`를 먼저 확인하고
일치하는 규칙이 없으면 `/etc/hosts.deny`를 확인한다. 두 파일 어디에도
일치하지 않으면 접근이 허용되므로, 기본 차단 정책은 허용 규칙을 먼저 확정한
후 적용해야 한다.

## 진단 예시

파일 존재 여부, 소유자와 권한을 확인한다.

```bash
sudo ls -al /etc/hosts.allow /etc/hosts.deny
sudo stat -c '%U %G %a %n' /etc/hosts.allow /etc/hosts.deny
```

주석과 빈 행을 제외한 활성 설정을 확인한다.

```bash
sudo grep -Ev '^[[:space:]]*(#|$)' /etc/hosts.allow
sudo grep -Ev '^[[:space:]]*(#|$)' /etc/hosts.deny
```

진단에서 확인된 현재 문제점은 다음과 같다.

- `/etc/hosts.allow` 파일에 활성 설정이 없다.
- `/etc/hosts.deny` 파일에 활성 설정이 없다.

## 권고 조치 방법

TCP Wrapper를 실제로 지원하는 서비스에 적용할 때는 두 파일의 소유자를
`root`로 설정하고 다른 사용자의 쓰기 권한을 제거한다.

```bash
sudo chown root:root /etc/hosts.allow /etc/hosts.deny
sudo chmod o-w /etc/hosts.allow /etc/hosts.deny
```

승인된 서비스와 접근 원천을 `/etc/hosts.allow`에 먼저 등록한 뒤 기본 차단
규칙을 `/etc/hosts.deny`에 설정한다.

```text
# /etc/hosts.allow
승인된_서비스 : 승인된_IP_또는_네트워크

# /etc/hosts.deny
ALL : ALL
```

허용 규칙 없이 `ALL : ALL`을 먼저 적용하지 않는다. 기존 SSH 세션뿐 아니라
모니터링, 백업, 중앙 로그 수집과 기타 관리 서비스 연결이 차단될 수 있다.

## OS별 유의사항

### Red Hat 계열 8 이상

RHEL 8에서는 `tcp_wrappers` 패키지가 제거됐으며 `/etc/hosts.allow`와
`/etc/hosts.deny` 내용은 접근제어에 적용되지 않는다. Red Hat은 서비스 접근
필터링에 방화벽 규칙을 사용하고 사용자·호스트 이름 기반 필터링은 서비스별
설정을 사용하도록 안내한다. Rocky Linux 등 RHEL 호환 배포판도 실제 지원
상태를 확인한 후 `firewalld`·nftables 또는 서비스별 접근제어로 설계한다.

단순한 다음 형태의 전체 차단 명령을 그대로 자동 적용하지 않는다.

```text
iptables -A INPUT -j DROP
```

기존 방화벽 관리 주체, zone, 인터페이스, IPv4·IPv6, 영구 설정 방식과 모든
필수 통신을 먼저 확인하지 않으면 원격 관리 접속이 끊길 수 있다.

### Ubuntu

Ubuntu 22.04는 TCP Wrapper 규칙 형식과 `libwrap0` 패키지를 제공한다. 하지만
두 파일은 TCP Wrapper 또는 libwrap 접근검사를 실제로 사용하는 서비스에만
효력이 있으므로, 파일 존재 여부만으로 조치 방법을 결정하지 않는다. 대상
서비스별 지원 여부를 확인하고, 지원하지 않는 서비스는 방화벽 또는 서비스
자체 접근제어 설정을 사용한다.

## 구현 상태

| 구분 | Red Hat 계열 | Ubuntu |
|---|---|---|
| 상태 | ⚪ 미구현(검토 보류) | ⚪ 미구현(검토 보류) |
| 실행 플레이북 | 미작성 | 미작성 |
| Role 태스크 | 미작성 | 미작성 |
| 현재 자동 조치 | 없음 | 없음 |

현재 저장소에는 U0218 점검 또는 설정 변경 플레이북이 없다. 파일 생성, 권한
변경, `ALL : ALL` 추가와 방화벽 변경을 수행하지 않는다.

## 미구현 사유와 우려사항

다음 사항이 정해지지 않아 자동 조치를 보류한다.

1. 서버별로 접근을 허용할 서비스와 프로세스 이름
2. Ansible 마스터노드, 운영자, 모니터링, 백업, 중앙 로그 등 승인된 원천
   IP·CIDR
3. IPv4·IPv6, 복수 인터페이스, NAT·프록시·로드밸런서 환경의 실제 접속 원천
4. Red Hat 계열의 `firewalld`·nftables 및 Ubuntu의 방화벽 관리 주체
5. 서비스별 TCP Wrapper 지원 여부와 애플리케이션 자체 접근제어 설정
6. 원격 접속 차단 시 사용할 콘솔 복구 절차와 롤백 기준

허용 목록 없이 기본 차단을 적용하면 Ansible이 대상 서버에 재접속하지 못하거나
업무·운영 통신이 중단될 수 있다. 또한 TCP Wrapper를 지원하지 않는 서비스에는
두 파일을 생성해도 실질적인 접근제어 효과가 없다.

## 구현 전 확정할 사항

- 서버 또는 서버 그룹별 승인 서비스 목록
- 관리·운영 시스템의 승인 IP 및 CIDR 목록
- 기존 방화벽 규칙과 외부 방화벽·보안그룹의 관리 주체
- OS 및 서비스별 실제 적용 수단
- 시험 서버 한 대의 콘솔 접근, 변경 전 백업과 자동 롤백 절차
- 새 관리 세션, 업무 통신과 차단 대상 통신의 검증 방법

위 항목이 확정되면 읽기 전용 현황 점검과 설정 변경 플레이북을 분리하고, 시험
서버 한 대부터 순차 적용하는 방식으로 구현한다.
